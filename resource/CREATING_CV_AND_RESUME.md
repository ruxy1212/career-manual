# LLM Instruction: Write High-Impact Technical CVs & Resumes

## Objective

Write a technically strong, recruiter-friendly CV that immediately communicates impact, credibility, and technical maturity.

The CV should not read like a list of responsibilities or technologies. It should present evidence that I solve meaningful problems, deliver measurable outcomes, and understand the business value of my work.

Every section should make a recruiter think:

> "This person has actually built things that matter."

---

# Overall Philosophy

Recruiters spend only a few seconds scanning a CV before deciding whether to continue reading.

The goal is not to mention everything I've ever done.

The goal is to make the important achievements impossible to miss.

Every sentence should answer at least one of these questions:

- What problem was solved?
- What changed because of this work?
- Why should anyone care?
- Why is this technically impressive?
- What business value did this create?

If a sentence answers none of those, it should be rewritten or removed.

---

# Write Like an Engineer, Not a Job Description

Avoid describing work the same way it appears in job postings.

Generic:

> Responsible for developing backend APIs.

Better:

> Designed and implemented REST APIs powering authentication, payments, and reporting across multiple internal services.

Generic:

> Worked on frontend development.

Better:

> Built responsive React interfaces that simplified complex workflows and reduced user friction.

The CV should communicate ownership, contribution, and outcomes—not merely participation.

---

# Prioritize Outcomes Over Activities

Recruiters already know what software engineers generally do.

Instead of explaining tasks, explain what those tasks accomplished.

Weak:

- Created dashboards
- Built APIs
- Managed databases
- Fixed bugs

Strong:

- Built operational dashboards that reduced reporting time for internal teams.
- Designed scalable APIs supporting growing application workloads.
- Optimized database queries to improve response times.
- Resolved production issues while strengthening long-term system stability.

Whenever possible, describe the effect of the work rather than the work itself.

---

# Demonstrate Technical Judgment

Strong engineers make decisions.

The CV should reflect technical thinking rather than simple implementation.

Instead of only describing what was built, explain why the chosen solution mattered.

Examples:

- Improved maintainability by restructuring application architecture.
- Reduced duplicated business logic through reusable service layers.
- Simplified deployment by introducing containerized environments.
- Improved reliability through better validation and error handling.
- Increased scalability by redesigning data access patterns.

These communicate engineering maturity.

---

# Show Business Impact

Technology exists to solve business problems.

Where possible, connect technical work to business outcomes.

Examples:

- Improved onboarding experience for new users.
- Reduced infrastructure costs.
- Increased application reliability.
- Enabled faster feature delivery.
- Supported business growth through scalable architecture.
- Reduced manual operational work through automation.
- Improved reporting accuracy for stakeholders.
- Accelerated internal workflows.

Recruiters remember engineers who understand why software exists.

---

# Use Technologies as Supporting Evidence

Technologies support accomplishments.

They are not accomplishments themselves.

Weak:

> Laravel, React, Docker, AWS, PostgreSQL.

Better:

> Built cloud-ready Laravel services deployed with Docker and integrated with PostgreSQL-backed applications.

Mention technologies naturally within achievements whenever possible.

Avoid long keyword lists unless required for ATS optimization.

---

# Quantify Wherever Truthfully Possible

Concrete evidence creates credibility.

Include metrics such as:

- years of experience
- applications delivered
- APIs developed
- concurrent users supported
- deployment frequency
- performance improvements
- infrastructure savings
- automation improvements
- datasets processed
- response-time improvements
- cost reductions
- processing speed
- user adoption
- feature delivery

Never fabricate metrics.

If numbers are unavailable, describe the outcome clearly instead.

Good:

> Simplified deployment across multiple environments.

Better than inventing:

> Improved deployment by 80%.

---

# Deep Project Intelligence & Authentic Metrics: /insights/

When tailoring a CV/Resume for a specific job, NEVER recycle the same 3 generic summary bullets or invent artificial numbers.

Instead, after selecting the top relevant projects or roles from `cv.md`, you MUST read the corresponding project file in the `/insights/` directory:
- `insights/{project-slug}.md` (e.g. `cardmajor.md`, `edulaw.md`, `musicstory.md`, `aura-spectrum.md`, `snipfair.md`, `trust-ledger.md`, `oja-link.md`, `demosaic-homes.md`, `animated-kangaroo.md`, `link-sharing.md`).

Each insight file contains verified, deep technical intelligence:
- **Architectural workflows:** Real polyglot persistence, failover mechanisms, queuing systems, and authentication flows.
- **Concrete engineering metrics:** Actual commit volume, route count, Eloquent model count, API endpoints, and database migrations.
- **Specific libraries & packages:** Exact SDKs, libraries, and frameworks used in production.
- **Technical trade-offs & bottlenecks:** Real problems faced and solved.

### The Rule for CV Customization:
1. Identify the target role's core technical priorities from the JD (e.g. distributed transactions, security/auth, audio/video streaming, client-side ML, or high-concurrency APIs).
2. Read the relevant `/insights/{project-slug}.md` files.
3. Select and highlight the specific metrics, subsystems, and architectural decisions from the insights that directly match what the hiring team is buying.
4. Keep the bullet points fresh, distinctive, and strictly grounded in real technical truth.

---

# Show Progression

The CV should communicate growth over time.

Avoid making every role sound identical.

Later experience should naturally demonstrate:

- larger systems
- greater ownership
- increased technical complexity
- architectural decisions
- mentoring
- leadership
- cross-functional collaboration
- product influence

Readers should see increasing responsibility without needing it explicitly stated.

---

# Demonstrate Breadth Without Losing Focus

Highlight versatility while maintaining a coherent narrative.

Instead of appearing as someone who has "used many technologies," present yourself as someone who solves related categories of problems.

Examples:

- scalable backend systems
- modern web applications
- cloud infrastructure
- AI-powered solutions
- automation
- data-driven decision systems
- developer tooling
- internal platforms

The technologies should reinforce the story rather than become the story.

---

# Avoid Generic Buzzwords

Replace empty adjectives with evidence.

Avoid phrases such as:

- hardworking
- passionate
- dedicated
- motivated
- self-motivated
- proactive
- detail-oriented
- team player
- fast learner
- results-driven
- dynamic professional
- innovative thinker
- go-getter

These communicate almost nothing because nearly every CV contains them.

Instead, allow achievements to imply these qualities.

---

# Avoid Empty Verbs

Avoid relying heavily on verbs like:

- responsible for
- assisted with
- helped
- participated in
- involved in
- worked on
- exposed to
- familiar with

These reduce perceived ownership.

Prefer verbs such as:

- designed
- built
- developed
- implemented
- optimized
- architected
- integrated
- automated
- deployed
- migrated
- improved
- streamlined
- modernized
- refactored
- analyzed
- transformed
- delivered
- scaled
- reduced
- enabled
- accelerated

Only use verbs that accurately reflect your contribution.

---

# Avoid Technology Dumps

Do not write achievements that are simply lists of tools.

Weak:

> PHP, Laravel, React, Docker, Redis, MySQL.

Better:

> Built Laravel APIs with Redis caching and MySQL, improving application responsiveness while supporting React-based frontends.

Context is always stronger than enumeration.

---

# Avoid Artificial Complexity

Do not exaggerate technical language.

Prefer clarity over sounding advanced.

Good engineers communicate clearly.

Avoid replacing simple explanations with unnecessary jargon unless the terminology genuinely improves precision.

---

# Be Specific

Whenever possible, replace vague wording.

Weak:

> Improved application.

Better:

> Improved checkout performance by reducing unnecessary database queries.

Weak:

> Optimized system.

Better:

> Reduced repeated API calls through server-side caching.

Specificity increases credibility.

---

# Make Every Bullet Independent

Each bullet should communicate a complete achievement.

A recruiter should understand the value of the bullet without needing surrounding context.

Avoid bullets that only make sense when read together.

---

# Avoid Repetition

Do not repeatedly describe the same achievement using different wording.

Avoid repeating:

- built APIs
- built backend
- developed backend
- created backend services

Instead highlight different dimensions:

- architecture
- performance
- scalability
- deployment
- integrations
- automation
- reliability
- security
- business impact

Each point should introduce something new.

---

# Optimize for Human Readers First

The CV should naturally contain important keywords for Applicant Tracking Systems (ATS), but readability should always come first.

Never sacrifice clarity just to insert keywords.

Keywords should appear naturally within meaningful accomplishments.

---

# Maintain Credibility

Never:

- exaggerate responsibilities
- inflate job titles
- invent metrics
- fabricate technologies
- imply ownership you did not have
- claim expertise you cannot defend in an interview

Every line should withstand detailed questioning.

---

# Strong Language Principles

Prefer language that communicates:

- ownership
- decision-making
- engineering judgment
- measurable outcomes
- technical depth
- business understanding
- scalability
- reliability
- maintainability
- user impact

Rather than language that merely communicates effort.

---

# Final Quality Checklist

Before producing the final CV, verify that:

- Every statement communicates value rather than activity.
- Responsibilities have been rewritten as achievements whenever possible.
- Business impact accompanies technical work where appropriate.
- Technical decisions are explained through their outcomes.
- Technologies support accomplishments instead of dominating them.
- Every metric is truthful.
- Empty buzzwords have been removed.
- Weak ownership verbs have been replaced with stronger ones where accurate.
- Each bullet communicates a distinct contribution.
- Repetition has been eliminated.
- The writing is concise, technically mature, and easy to scan.
- The CV sounds like it was written by an experienced engineer, not generated from a generic template.
- Every sentence earns its place by increasing the recruiter's confidence in my ability.
